Pixelette Group · Internal Method Document · v1.1

The Group Revamp Playbook

How to convert any Pixelette group website onto the shared pattern guide without erasing what makes that company itself. This is the method, generalised from the first conversion, written to be handed to whoever — person or agent — does the next one.

This document is self-contained. It carries the method, the canonical shared-layer values and the source of the tooling, so no access to any previous conversion's repository is needed or expected.

Section 00

How to use this document

You are about to convert one Pixelette group website onto the company-wide design language. This document is the workflow. It was derived from the first completed conversion (Pixelette Certified) and is deliberately written so that nothing in it is specific to that site — the Certified specifics appear only in boxed worked examples, clearly marked, as illustration.

Read this document end to end before writing a single line of code. Then work the phases in order. Phases A to C produce no code at all; they produce an audit, a derived palette and a plan, and all three go to the user for sign-off before implementation starts. Skipping straight to implementation is the most expensive mistake available here, because the constraints in Section 02 silently invalidate a lot of otherwise-good design work, and you will find that out only after building it.

The one-sentence version

Take the look and feel from the pattern guide; keep the substance — content, colour, imagery, widgets, data — from the site you are converting. Every group site ends up with the same bones and a different face.

What you have, and what you still need

You are not given the previous conversion's codebase, and you do not need it. Everything that conversion produced which is of use to you is in this document: the method, the trap catalogue, the canonical values for the layer that must not vary (Appendix E), and the source of the gate script you will build (Appendix B). Treat those as the group's shared property, already derived and signed off — do not re-derive them, because re-derivation is how a group design system silently forks.

Three inputs are required before Phase A can start:

InputStatusIf you do not have it
This playbook Supplied —
The repository of the site being converted Supplied Stop and ask. Nothing in Phase A is possible without it.
The pattern guide — the HTML mockup issued by Mr Rana Must be provided separately Stop and ask for it before writing anything. Appendix E gives the shared values but not the page-level compositions, and you cannot infer those.
Do not substitute Appendix E for the guide

Appendix E is the numeric layer — scale, geometry, type roles, the component class inventory. The guide is the compositional layer: what a hero looks like, how a card grid is laid out, what a page of each type is made of. You need both. If only Appendix E is to hand, you can build the token layer and the primitives, and you must stop before Phase D4.

Section 01

The premise: two inputs, one output

Every conversion in this programme has exactly two inputs, and they are authoritative over different things. Confusing which input governs which decision is the root cause of most of the errors catalogued in Section 09.

InputAuthoritative overNot authoritative over
The pattern guide
an HTML mockup issued by Mr Rana		 Layout, spacing rhythm, type roles and scale, radii, shadows, section anatomy, component anatomy, the flat and static register, tap targets, the container width. Colour. Copy. Which sections exist. Imagery. Which widgets a page carries. Anything the guide happens to say about a company that is not the one you are converting.
The existing codebase
the live site being converted		 Every word of copy. Section inventory and order. Brand colour. Logo and imagery. Data, widgets and interactive features. Routing, SEO, structured data, integrations. How any of it looks. Existing visual decoration, motion, glassmorphism, gradients and shadows carry no authority and are expected to go.

The output is a single site that a visitor would place in the same family as its siblings at a glance, and would never mistake for one of them.

Why colour comes from the codebase, not the guide

This is the least obvious rule and the one worth internalising first. The pattern guide is drawn in one company's colours because it had to be drawn in some colour. Copying it faithfully produces a site that reads as that company, which defeats the exercise.

More importantly, the brand palette usually already exists in the repository and is usually already correct. The logo files, the wordmark SVG, the favicon and the original stylesheet are the evidence. When they disagree with each other, the wordmark is the tiebreaker: it is the asset that has been printed, signed off and used externally, and the stylesheet is the thing that drifted.

Rule

You are not inventing a palette. You are recovering the one the company already owns and expressing it in the structure the guide provides. If you find yourself choosing a hue you like, stop — you have skipped the audit.

Section 02

The law: fixed, free and forbidden

Fixed — the family resemblance

These are shared across the whole group. If a site changes them, the group has no visual coherence and there was no point running the programme. Do not vary them, and do not vary them “slightly”. The canonical values are in Appendix E — they were derived from the guide once, during the first conversion, and signed off. Copy them; do not re-derive them from the guide, because two independent derivations will not agree and the divergence will not be visible until the sites are seen side by side.

  • Container. The wrap width and gutters, unchanged.
  • The fluid type scale. Every clamp, interpolated between the two widths the guide specifies. Take them verbatim from Appendix E.
  • Type roles. Serif for display, sans for body, mono for eyebrows and figures, sans for the small heading. The faces are group property. Weight may be tuned by eye with the user; the face may not be swapped.
  • Geometry. Card radius, button radius, tile radius, and the shadow set. Three shadows, no more.
  • Section anatomy. Eyebrow, then heading, then lead, then content. Hairline rules, alternating light bands, generous vertical rhythm.
  • Register. Flat and static. Editorial, not decorative.
  • Accessibility floors. 44px minimum tap targets, visible focus on every control, body text held at 16px.

Free — what makes this site itself

Five levers, listed in descending order of how much distinction they buy. Use them in this order; the first two do most of the work.

  1. Value structure. Not hue — value. See Section 04.
  2. Neutral rotation. Hold every neutral's lightness exactly and rotate its hue toward the brand. Costs nothing measurable and changes the feel of every page.
  3. Dark family temperature. The footer and any dark panel bookend every page; two tokens, high leverage.
  4. One signature device. Exactly one memorable mannerism, built from primitives the guide already contains. One. Not two.
  5. Hero ground and widget. See Section 07.

Forbidden

Hard constraint — content does not change

Every heading, paragraph, list item, testimonial, FAQ, statistic, label and call-to-action stays byte-identical. No section is added, removed or reordered. This is a UI conversion only, and it remains in force for every follow-up commit on the branch, not just the first one.

Two corollaries that catch people out:

  • Layout and alignment may change freely; DOM order of content may not. Moving an element to match the guide's ordering is a content change.
  • A bug fix that requires new visible text is out of scope. Log it, raise it, do not ship it.
Hard constraint — no regression in SEO or structured data

Every metadata export and every JSON-LD block must keep emitting exactly what it emits today. Verify by diffing the emitting code rather than by diffing rendered output; the command is in Section 08.

Also forbidden without explicit instruction: pushing the branch, opening a pull request, and deploying. Committing in logical chunks on the working branch is expected and encouraged.

Section 03

Phase A — Research

No code is written in this phase. The deliverable is an audit the user can read in five minutes and correct.

A1 Read the repository's own instructions first

Look for AGENTS.md, CLAUDE.md, README and anything in .claude/. These override general practice. In this programme at least one repo carries a warning that its framework version has breaking changes against model training data and that the vendored documentation under node_modules must be read before writing framework code. Take such warnings literally.

Output A short list of repo-specific rules you are now bound by.

A2 Inventory the existing site

  • Every route, including dynamic ones. Count them; you will need the number to verify the build later.
  • Every section component and where it is used.
  • The client/server component split, and every file carrying a client directive.
  • Every dependency the visual layer touches: animation libraries, icon sets, typography plugins. Check that each is actually installed — classes referencing an uninstalled plugin are a live bug, not a style choice.
  • Integrations that must not break: forms, chat widgets, analytics, captcha, email templates, CMS or database reads.
Output A route table and a component inventory.

A3 Audit the existing colour

This feeds Phase B and is the most important research step.

  • Extract every colour from the logo and wordmark SVG files. Note them exactly.
  • Extract the favicon's colours.
  • Enumerate the colour tokens the current stylesheet defines.
  • Grep the whole source tree for raw hex values and count them per file. Expect the count to be high and concentrated in a few components; expect email templates and any constants file to hold their own separate, probably stale, copy of the palette.
  • Record every disagreement between these sources. The wordmark wins.
Output A table of every colour in the repo, its source, and which of them agree. Flag the drift explicitly.

A4 Read the pattern guide as a specification

  • Extract its token values, its type scale, its spacing rhythm, its radii and shadows.
  • Note the two viewport widths it is drawn at — the fluid scale interpolates between exactly those, and both endpoints should land on spec.
  • Catalogue every component pattern it defines, and note what it does not define. A static mockup typically has no focus states, no transitions, no disabled states and no keyframes. Those you will design, and they should be designed once for the group.
  • Look for the guide contradicting itself. Where the guide renders the same component in a different accent, or assigns each company a different treatment, that is not an inconsistency — it is the author sanctioning variation, and it is your permission slip. Quote it in your plan.
Output A specification extract, plus a list of the guide's own sanctioned variations.

A5 Map guide patterns to site sections

For each section of the existing site, name the guide pattern it will become. Where the site has something the guide has no pattern for, say so now and propose a derivation from guide primitives. Where the guide's pattern needs copy the site does not have, say so now — the resolution is always to ship the pattern without the missing element, never to write the copy.

Output A section-by-section mapping with the gaps called out.
Gate

Give the user the audit before proposing anything. Colour drift in particular is a finding they will want to see, because it usually means something shipped wrong a while ago.

Section 04

Phase B — Derive the brand layer

Still no site code. The deliverable is a proposed palette with contrast arithmetic attached, and a way for the user to look at it.

The central insight: hue is not the differentiator

Two companies in this group can sit within ten degrees of hue of each other. Swapping one brand colour for another that close produces a site that reads as the same site with a fault in it. The distinction has to come from somewhere else, and the place it comes from is value structure: how many tones the brand runs, and what job each tone does.

One-tone structure

A single mid-value brand colour does every job — eyebrow, link, button fill, card border, wash. Calm, uniform, slightly corporate.

Two-tone structure

A dark anchor carries everything that is read; a bright signal marks and never speaks. Same bones, unmistakably a different company.

Other structures are available and worth considering: a warm accent over a neutral anchor, a three-step ramp where the mid tone does interface work and the extremes do emphasis, a near-monochrome scheme where the brand appears only at section openings. Pick the structure that the company's existing assets already imply. If the wordmark has two colours, the site probably wants two roles.

Rule — roles, not shades

Name every brand token by the job it does, not by how light it is. A token called brand-signal that is barred from text will survive a redesign; a token called brand-light will be misused within a week.

The contrast arithmetic is not optional

Compute the contrast ratio of every brand token against every ground it will sit on, and write the numbers into your proposal. Do this before designing anything on top of them, because the numbers routinely veto the obvious choice.

ThresholdApplies toConsequence if missed
4.5:1Body text, and any text below 24px or below 19px bold.Fails WCAG AA. Not shippable.
3:1Large text, and non-text elements that carry meaning: borders that identify a control, icon strokes, focus rings, chart marks.Fails WCAG 1.4.11. Not shippable.
<3:1Nothing that must be perceived. Decorative fills only.Invisible to a meaningful share of users.

Two rules follow from the arithmetic, and both have already cost real work in this programme:

Trap — the bright brand colour cannot become the text colour

A vivid brand colour that looks correct in a logo is frequently below 3:1 on white. It cannot become the reading colour by direct substitution, because the guide's structure uses the brand colour for eyebrows, inline links, tick glyphs, icon strokes and filled buttons — often across dozens of call sites. Establish a darker reading tone for those, and restrict the bright tone to solid non-text marks of adequate size, typically a 3px accent.

A brand colour at roughly 3:1 clears the non-text threshold and nothing else. Never text, never a thin stroke. Icons at a light stroke weight read as washed out even when the ratio technically passes, so send them to the anchor tone.

The inverse is also true

On a dark ground, the bright tone is usually free — frequently above 5:1 — and can speak as text. That is what makes a dark hero or a dark panel the one place the signal colour gets a voice. Buttons may need to invert there: a dark brand fill on a dark ground disappears, so the fill becomes the bright tone with near-black label text.

Rotate the neutrals

Take the guide's neutral ramp and, for every entry, hold the lightness exactly and rotate the hue toward the brand. Nothing measurable moves — every text contrast ratio holds or improves — but the page feels like a different building. It is the cheapest convincing distinction available. Do the same for the dark family: footer and panel tokens shift temperature together.

Choose one signature device

One mannerism, assembled from what the guide already has, applied consistently. Move an accent the guide places on one edge to another edge; cap a rule with a short segment of brand colour; give one card type a distinguishing border. It should be expressible in two or three CSS rules and be removable in one revert. Resist adding a second, because two mannerisms read as decoration and the register is flat and static.

Build the comparison page

Generate a single HTML page that renders the guide's palette and yours side by side, using specimens lifted from the real stylesheet at build time rather than hand-written swatches, so what you are looking at is the actual site. Include the measured contrast ratio next to every pairing, and badge any failure that is inherited from the guide differently from one you introduced — the user needs to see it without it being misattributed.

Invert it once it is signed off

The comparison page starts as a decision instrument, with the guide frozen on one side and your proposal on the other. The moment the palette lands in the stylesheet, both columns render identically and it silently stops comparing anything. Invert it: freeze the signed-off values in the generator, keep extracting the live ones from the stylesheet, and fail the build if they diverge. It then earns its keep permanently as a regression check. If you fork the generator for the next site, invert it there too.

Gate

The palette is signed off by eye, by the user, on the comparison page. Not by you, and not by the arithmetic alone — the arithmetic only vetoes.

Section 05

Phase C — Plan

Write the plan down and get it approved before implementing. It must contain, at minimum:

  1. The phase list with a commit boundary for each, in the order given in Section 06.
  2. The token table as signed off, with roles named and ratios attached.
  3. The section mapping from Phase A5, including every gap and its resolution.
  4. The judgement calls the content constraint forces, listed explicitly as a table of situation and resolution. These become settled decisions; recording them stops them being relitigated three days later.
  5. What will be deleted, named file by file.
  6. What will not be touched: structured data, metadata, state, network calls, storage, third-party widget configuration.
  7. The verification plan, terminal and browser separately.
State the cost of the constraint before building, not after

If the content rule removes the part of an idea that justified it, that idea is probably dead. Say so in the plan and either get the new copy signed off first or pick a different idea. Building the gutted version and showing it is a waste of a cycle, and it will be rejected by eye without anyone being able to say precisely why.

Expect the site to look deliberately incoherent partway through the conversion. Say that in the plan so nobody reviews it mid-flight and panics.

Section 06

Phase D — Implement

The order matters. It moves from the foundation outward, so each phase compiles against a layer that is already correct.

D0 Token layer and fonts

Rewrite the global stylesheet from scratch rather than editing the old one; you are replacing a design system, not adjusting it. Install the fonts. Update the manifest and the browser theme colour, which are easy to forget and will otherwise contradict the new palette on mobile.

Banner-mark the stylesheet into two parts: a brand layer holding the colour block and the signature device, and a common layer holding radii, shadows, container, the scale and every component class. The brand layer is the only part that differs per company; keeping the boundary visible is what makes the next conversion cheap.

Commit One, on its own.

D1 Shared primitives

Rewrite buttons, cards, headings, accordions, breadcrumbs. Add the small primitives the guide implies — eyebrow, pill, stat tile, an icon set traced from the guide at its stroke weight. Everything downstream depends on these, so they land before any page does.

D2 Delete the decorative layer

Particle canvases, custom cursors, floating orbs, dot grids, gradient text, glow shadows and every entrance-animation wrapper. Be thorough and count what you removed; the count is a useful assertion later. Motion survives only where it is functional: a drawer, a menu, an accordion, a chat overlay.

D3 Chrome

Header and footer. These bookend every page, so doing them early makes every subsequent page reviewable.

D4 Homepage

Every section, in place, including inline blocks that never became components.

D5 Interior pages

Templates first, since one template usually drives many routes, then the standalone pages, then index and detail pairs, then the legal pages. Nothing here is optional; a single unconverted page is what someone will land on first.

D6 Embedded products and widgets

Chat widgets, configurators, calculators, anything with its own visual identity inside the site. Detokenise rather than hex-swap. Replacing raw hex values with token references costs the same effort once and means the widget follows the palette permanently instead of drifting a palette behind at the next change.

Colour only. Do not touch state, network calls, storage, or third-party widget configuration while you are in there.

D7 Transactional email and favicon

The places colour hides. HTML email cannot read custom properties, so it needs its own exported constant — give it one, make both templates import it, and delete any stale unused colour constant you find, because an unused palette constant is exactly how email drifts.

Re-cut the favicon to agree with the wordmark.

D8 Cleanup

Delete the animation helpers, the compatibility shims, the temporary legacy-token block and any deprecated component props the conversion made redundant. Delete primitives you built but never imported — if the CSS class turned out to be the natural way to write the markup, the React wrapper is dead code. Do not rebuild it without a call site.

D9 The brand layer and the signature device

If you derived the palette in Phase B you may already have landed it in D0. If the conversion ran first on the guide's own colours, this is where the site stops looking like the guide's company. Either way it is its own reviewable commit, or small series of them.

Commit discipline

Logical chunks on the working branch, one concern per commit, so each step is reversible and the diff is reviewable. Do not push, do not open a pull request, do not deploy without being asked.

Section 07

Phase E — The hero

The hero is where a visitor decides which company they are looking at, so it gets its own phase. The method is the same as the brand layer: freeze the anatomy across the group, vary exactly one or two cells.

Freeze this sequence everywhere:

ground  →  eyebrow / pills  →  heading  →  lead  →  action pair  →  widget

Then choose one ground and one widget.

GroundNotes
Centred light washThe guide's default homepage treatment.
Offset light washUsually the interior-page variant; can be promoted.
Dark inverse groundBuilt from the existing dark panel tokens, so it needs no new colour. The one place the bright brand tone can be text. Buttons must invert.
Tinted washA brand-derived tint rather than near-white. Quiet, and reads as deliberate.
WidgetVerdict
Statistic tile stripThe default every site inherits from the guide. Zero invention, but shared, so it distinguishes nothing on its own.
Credential or capability ledgerA hairline grid replacing a pill cloud. Only worth doing if it can carry a second column of status or value copy — which is new copy, so get it signed off before building. Without it, it is a pill cloud in a grid, and it will be rejected.
Proof cardA single feature card carrying a short ruled sequence. Reinforces the signature device, or competes with it. Judge which.
Asymmetric data columnRuled out. That is a layout change, and layout is on the fixed list.
Composed seal or badge markRuled out. Returns to the decorative register the conversion exists to delete.
Motion groundAvailable only with explicit user request, and see the warning below.
If motion is requested

Flat and static is a group rule, so any motion is an exception and must be scoped like one: one section, one component, mounted with positioning at the call site so the global stylesheet never learns about it, and removable in a single revert. It must render nothing under prefers-reduced-motion, pause when off-screen, be gated away from touch input, and read its colours from live tokens with no hard-coded fallbacks.

It must also obey the palette rules rather than sidestep them: solid marks may take the bright signal tone, thin connecting strokes may not.

Leave a note for the group. If more than one site ends up with a motion ground, flat and static is no longer a group rule and the pattern guide needs amending with its author rather than being quietly diverged from.

Expect the first hero to be rejected

The hero is the one element decided purely by eye. Build it, show it, and be ready to revert cleanly — keeping any unrelated change that happened to land in the same file. Record the reasoning and the measured figures even for a rejected attempt: they transfer to the next site, and the next agent should not have to rediscover them.

Section 08

Phase F — Gates and verification

Automated gates

Three of these are standard for the stack. The fourth is specific to this programme and you should port it to every site.

GateExpectation
Type checkSilence.
LintZero errors. Record the pre-existing warning count before you start so you can prove you did not add any.
Full production buildEvery page generated. Compare the count against the route table from Phase A2.
Token gateCustom script. See below and Appendix B.
Palette regressionCustom script. Fails the build if the stylesheet drifts from the signed-off palette.
Why the token gate exists

Modern utility-first CSS emits nothing for an unknown utility. A retired class left behind after a token rename renders as inherited colour with no build error and no warning. The failure is completely silent and can survive a full review.

So write a script that fails on three things: retired utility names, retired hex values from the previous palette, and raw hex anywhere in the source outside a small exempt list. Exempt files individually, each with a stated reason in a comment — typically the email colour constants, the stylesheet that defines the tokens, the web app manifest, and any severity colours that are not palette.

Keep the matcher deliberately dumb: no comment parsing. That means provenance notes in the stylesheet must write bare values without a hash, or the gate trips on its own documentation. Follow that convention.

Structured data non-regression

Do not diff rendered output across two builds; diff the emitting code and expect it empty.

git diff -- src/components/seo/ src/app/layout.tsx    # expect no output

Then record, per page, which structured-data blocks the built HTML actually emits, and check the table again at the end. Where a component takes a flag to suppress a duplicate block, that is deliberate; do not helpfully re-enable it.

Assertions worth grepping

  • Zero decorative utilities remaining.
  • Zero dark-theme utilities outside the components that are meant to be dark.
  • The animation library down to an exact expected number of importers.
  • Client directives down to an exact expected number of files.
  • The new tokens present in the built CSS chunk, and the retired values absent from it. Note that the built stylesheet may be a hashed chunk in an unexpected directory; find it rather than assuming the path.

The browser walk — not optional, and not something you can do from a terminal

The standing failure mode of this programme

Every terminal gate can pass on a conversion that has never been looked at. That is the state the first conversion sat in for a long time, and it is worth naming: a clean build is not visual sign-off. Say so plainly in your status reports rather than reporting the gates and letting them imply more than they prove.

Walk every static route plus one instance of each dynamic route, and check:

  • Each page against its guide counterpart at the guide's wide width.
  • The same at the guide's narrow width. The scale interpolates between exactly those two, so both endpoints should land on spec.
  • The signature device, at both widths.
  • Any embedded widget or chat overlay on the new palette.
  • Keyboard only: visible focus on every control, skip link, menus, drawer, accordion, form submission.
  • Reduced motion switched on at the OS level, observed running — not merely present in the code.
  • Touch behaviour for anything gated to fine pointers.
  • One real form submission per form, to see the resulting email rendered.
  • Error states, which are the states nobody looks at.

Fixes arising from the walk go in follow-up commits on top of the conversion commits, which stay legible as the baseline.

Section 09

The trap catalogue

Every one of these has actually happened. They are listed in the order you are likely to meet them.

Trap 01 — Inventing guide-shaped labels

The guide's sections nearly all open with a mono eyebrow. Your sections often have no such copy. The pull to write one is very strong and it is a content change. It happened twice in the first conversion and both were reverted.

Rule: if the copy is not already in the file, it does not go on the page. Where the guide demands a label you cannot supply, ship the pattern without it.

Trap 02 — Reordering to match the guide

Moving hero pills below the buttons, or a star row below a quote, to match the guide's ordering. This is a content change and it will be reverted.

Rule: layout and alignment may change freely; DOM order of content may not.

Trap 03 — Fixing a bug by adding copy

You will find real bugs. Some of them — a form that sets an error state and renders nothing for it — can only be fixed by adding visible text.

Rule: log it, raise it as a separate change, do not ship it inside the conversion.

Trap 04 — Building the gutted version of an idea

When the content constraint removes the element that made a design worth doing, the remainder is usually worse than the thing it replaced, and it gets rejected by eye without a clear reason — quite possibly because the justification was removed.

Rule: when the constraint guts an idea, say so before building it.

Trap 05 — The naive palette swap

Substituting the company's bright brand colour directly for the guide's brand colour. It will be below the text threshold on white and it will break every text call site and every filled button at once. See Section 04.

Trap 06 — Hard-coded hex inside a component class

A rule that writes a literal colour instead of reading its token escapes the palette change silently and sits a full palette behind everything around it. This is exactly what the token gate is for, and it has caught real instances in closing bands, footer pills, email constants and a brand-new file written after the gate existed.

Trap 07 — Cascade layer and specificity mistakes

If the framework declares an empty components layer, every hand-written class must go inside it, or an unlayered class outranks every utility on the site and class="card p-0" stops behaving. Likewise, inline theme variables may not be emitted to the document root at all — component classes must reference whichever variable name is actually emitted. Check both against the framework's own vendored documentation, not from memory.

Trap 08 — Preflight versus the guide

A CSS reset zeroes heading sizes and weights, strips list markers and makes links inherit colour. The guide assumes none of that. Also, do not copy the guide's global coloured link rule — it will turn the navigation, breadcrumbs and footer brand-coloured. Make inline links opt in through a class, and let article bodies get it automatically.

Trap 09 — Building primitives nobody imports

Wrapper components for layout and typography tend to lose to plain CSS classes, which are the natural way to write the markup. Build them only when a call site demands them, and delete the ones that never got imported.

Trap 10 — Deleting motion that was requested

If an earlier phase deleted all decoration and a later phase added one sanctioned motion surface back at the user's request, a future pass will read it as leftover decoration and remove it. Document the exception at the point where the rule is stated, not somewhere else.

Trap 11 — Assuming shell portability

Scripts that work in a POSIX shell fail when npm runs them through a Windows command interpreter. Write gate scripts in the runtime you already depend on, not in shell. See Appendix C.

Faults inherited from the guide are not yours to fix unilaterally

You will find defects that come from the pattern guide itself and are therefore identical across every company — an outline button identified purely by a border that falls well below the 3:1 non-text threshold is the known example. Fixing it on one site silently forks the group design system.

The correct handling: fix nothing, report it clearly, mark it in the comparison page as inherited rather than introduced so it is visible without being misattributed, and raise it with the guide's author as a change to the shared layer.

Two open group-level questions currently sit with the guide's author. Carry them forward and add to the list rather than resolving them locally:

  • Whether a motion hero ground is available to every site or remains a single exception. If every site gets one, flat and static is no longer a group rule.
  • The inherited outline-button contrast failure, which needs a dedicated border token in the shared layer.

Section 11

Keep a vault

A conversion runs across many sessions. Keep a small set of linked notes in the repository, gitignored so they never ship, holding the state that is not recoverable from the code or the commit history.

The set that worked, and which this document was distilled from:

  • An index note. Branch state, the commit table, where things stand, standing instructions from the user, and links to everything else. This is the note a fresh session reads first, so it must be accurate about what has and has not been verified.
  • Design system. Live token values, the component class inventory, and the two or three framework mechanics that will otherwise waste an afternoon.
  • Brand layer. Why this site's palette is what it is, the levers used, and what must never move. The note the next site's agent actually needs.
  • Hero strategy. The matrix, what was tried, what was rejected and the measured figures behind both.
  • Build and verification. Commands, required environment variables, the gates, and the environment hazards.
  • Known bugs and deviations. Fixed, deliberately left, and deviations from plan with reasons.
  • Rules. The standing constraints and every trap that actually bit, written up at the moment it bit.
Write down rejected work

A design that was built and rejected is worth more written down than deleted, because the reasoning and the contrast figures transfer to the next site. Record what it was, why it was sound, and the most likely reason it failed.

Section 12

Definition of done

  • Audit, palette and plan were each signed off before the code they governed was written.
  • Every route converted. None missed.
  • Content byte-identical: no added, removed or reordered sections, no edited copy.
  • Structured data and metadata provably unchanged.
  • Type check silent; lint at zero errors with no new warnings; full build generating the expected page count.
  • Token gate clean: no retired utilities, no retired hex, no raw hex outside the stated exemptions.
  • Palette regression check in place and passing, inverted so that it actually compares.
  • Brand layer and common layer separated and banner-marked in the stylesheet.
  • Exactly one signature device.
  • Every brand token's contrast ratio recorded against every ground it sits on, with the bright tone confined to solid non-text marks on light grounds.
  • Dead code deleted: unused primitives, animation helpers, shims, stale colour constants.
  • The browser walk completed at both scale endpoints, including keyboard, reduced motion, touch, error states and one real submission per form.
  • Vault notes current, including anything built and rejected.
  • Inherited guide faults reported, not silently fixed.
  • Branch committed in logical chunks. Not pushed, no pull request, not deployed, unless explicitly asked.

Appendix A

Worked example: the first conversion

Pixelette Certified, converted across three phases. Included as illustration of the abstract steps above. Do not copy the values — copy the reasoning.

What the two systems were

The existing site was dark-first and decorative: a dark petrol ground, a bright teal, glassmorphism, glow shadows, gradient text, blurred floating orbs, an animated particle canvas, a custom cursor, and an entrance animation on every section. The guide was light, editorial, flat and static: white on pale bands, a single green, hairline rules, light serif headings, mono eyebrows, 12px cards, 4px buttons and no motion at all. Two near-opposite systems, so the work was to replace the design system underneath unchanged content.

The three findings that set the direction

  1. The wordmark was already right. Both logo files had always carried the company's own two colours; only the stylesheet and the favicon had drifted to the guide's green. The task was never to invent a palette — it was to bring the site back into agreement with its own mark.
  2. The guide sanctions accent swapping. It renders one of its own sections in amber: same card, same eyebrow, same border, different accent. The pattern surviving a hue change is demonstrated in the author's own document.
  3. Hue was not the differentiator. The guide's green sat at 173°; the company's teal at 180° and its petrol at 182°. Nine degrees across the whole set, which is precisely why the obvious swap reads as a fault rather than as a different company.

The value structure that resulted

One-tone versus two-tone

The guide's company is one-tone: a single mid green does every job.

Certified became two-tone: a dark petrol anchor carries everything that is read; a bright teal signal marks and never speaks.

Measured: the anchor at 8.71:1 on white, its hover state at 11.40:1, and the signal at 3.04:1 — clearing the non-text threshold and nothing else, hence restricted to solid 3px accents on light grounds. The company's original teal measured 2.86:1 on white, so a direct swap would have broken 61 text call sites plus every filled button. On the dark footer the signal measures 5.04:1 and is free.

The signature device

Two CSS rules. The guide accents the top of a feature card; Certified moved that accent to the left, and capped section rules with a 40px segment of signal colour. Deliberately not applied to every band — it marks a section opening, not a background change.

What was tried and rejected

A dark inverse hero ground with a credential ledger replacing the hero pill cloud. Every gate passed; it was rejected by eye. The reasoning was sound and is preserved: the dark ground is the one place the signal colour can be text, at 5.94:1; it needed no new tokens because the dark panel family already was that petrol; the filled button had to invert because the anchor fill measured 2.08:1 on that ground and disappeared. The likely cause of the rejection was that the ledger could not carry the status column that justified it, because that column was new copy. That is Trap 04 in the catalogue.

What shipped instead

A cursor-reactive particle field behind the homepage hero, at the user's explicit request — the single sanctioned exception to flat and static, scoped to one component, absent under reduced motion, gated away from touch, reading both its colours from live tokens, and respecting the signal rule: the bright tone paints the dots, which are solid marks, while the joins take the anchor tone because a 1px line is a thin stroke. This is Certified-specific and is not inherited by other sites unless the group question in Section 10 is resolved in its favour.

Real bugs the conversion uncovered

  • Accordion answers were unmounted when collapsed, so FAQ content was invisible to crawlers and to in-page search across every service page. Panels stay mounted now.
  • Article bodies were styled with a typography plugin that was not a dependency, so they had been rendering unstyled.
  • Reduced motion was declared in CSS but not honoured, because CSS cannot stop a JS animation library writing inline transforms.
  • Sub-44px tap targets throughout the footer and category chips.
  • An unused, stale colour constant, which was how the transactional emails had drifted a full palette behind the site.
  • A form that sets an error state and renders nothing for it. Logged, not fixed — the fix needs new copy.

The token gate — full source

Adapt the three marked regions to your site and use it as it stands. It is deliberately small; its value is entirely in being run on every change.

/**
 * Fails if colour has escaped the token layer.
 *
 * Utility-first CSS emits NOTHING for an unknown utility, so a retired class
 * left behind after a token rename renders as inherited colour with no build
 * error and no warning. This gate is the only thing that catches that.
 */
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join, relative } from "node:path";

// On Windows import.meta.url yields /D:/... so strip the leading slash.
const ROOT = new URL("..", import.meta.url).pathname.replace(/^\/([A-Za-z]:)/, "$1");
const SRC = join(ROOT, "src");

// ADAPT 1. Retired utility names: the utility prefixes crossed with the token
// names you are retiring from the old design system.
const PATTERN =
  /\b(bg|text|border|from|via|to|ring|fill|stroke|outline|divide)-(primary|accent|surface|glass)(-(light|dark|border))?\b/;

// ADAPT 2. The previous palette, enumerated. Anything still carrying one of
// these has been missed by the palette change and will render a full palette
// behind everything around it, silently.
const RETIRED_HEX = /#(AAAAAA|BBBBBB|CCCCCC)\b/i;

// Raw hex anywhere else. Colour belongs in a token so that the next brand
// layer is one file to edit rather than an archaeology exercise. Pure white
// and black are not palette colours and are always allowed.
const RAW_HEX = /#(?!(?:FFF{1,4}|FFFFFF|000|000000)\b)[0-9A-Fa-f]{6}\b/i;

// ADAPT 3. Files where a literal hex is unavoidable, each with a stated reason:
//   constants     email colour export - HTML email cannot read custom properties
//   globals.css   defines the tokens in the first place
//   manifest.ts   PWA manifest is JSON, consumed outside the document
const RAW_HEX_EXEMPT =
  /^src[\\/](lib[\\/]constants\.ts|app[\\/]globals\.css|app[\\/]manifest\.ts)$/;

const hits = [];

function walk(dir) {
  for (const entry of readdirSync(dir)) {
    const full = join(dir, entry);
    if (statSync(full).isDirectory()) { walk(full); continue; }
    if (!/\.(tsx?|jsx?|css|mdx?)$/.test(entry)) continue;
    const rel = relative(ROOT, full);
    const rawHexAllowed = RAW_HEX_EXEMPT.test(rel);
    readFileSync(full, "utf8").split("\n").forEach((line, i) => {
      const at = `${rel}:${i + 1}: ${line.trim()}`;
      if (PATTERN.test(line)) hits.push(["retired utility", at]);
      else if (RETIRED_HEX.test(line)) hits.push(["retired palette hex", at]);
      else if (!rawHexAllowed && RAW_HEX.test(line)) hits.push(["raw hex, use a token", at]);
    });
  }
}

walk(SRC);

if (hits.length > 0) {
  console.error("Colour that has escaped the token layer:\n");
  for (const [kind, at] of hits) console.error(`  [${kind}] ${at}`);
  console.error(`\n${hits.length} occurrence(s).`);
  process.exit(1);
}

console.log("No retired colour tokens found.");
Keep the matcher dumb

It does not parse comments, so a provenance note in the stylesheet that writes a retired value with a hash will trip the gate on its own documentation. The convention is to write such notes bare — was 414D5C, no hash. Costs nothing, and keeping the matcher simple is what keeps it trustworthy.

The palette comparison generator — specification

The original is around 1200 lines, most of which is site-specific specimen markup, so it is not reproduced here. Build your own to this specification; the design is what matters, not the code.

  1. Extract, do not transcribe. Read the live stylesheet at build time and pull out the token block, the fluid scale block and the component-class layer by locating them in the source text. Unwrap the component classes from their cascade layer, since a standalone page has no utilities to out-rank. Pull the one media query verbatim so narrowing the page reproduces the real responsive behaviour. The point of extracting rather than hand-writing swatches is that the specimens are then the actual site.
  2. Render two columns. The guide's frozen values on one side, the live extracted values on the other. Include a specimen board covering every class that carries a brand or neutral token, and one full page-shaped composition in real copy, because tokens judged in isolation read differently from tokens judged in context.
  3. Attach the arithmetic. Compute and print the contrast ratio for every token-against-ground pairing. Give each check a kind that selects its threshold: text at 4.5, large text and non-text at 3. Print the number, not just a pass mark.
  4. Badge failures by provenance. A failure inherited from the guide is badged differently from one you introduced — amber against red is enough. This matters: an inherited fault must be visible without being misattributed to your work, and it is what lets you report it upward rather than fixing it unilaterally.
  5. Then invert it. Once the palette is signed off, freeze the approved values in a constant inside the generator and have it compare those against what it extracts from the live stylesheet. Exit non-zero on any drift, and make the error message say that an intentional token change means updating the frozen constant too. Until you do this, the page silently stops comparing anything the moment the new palette lands, because both columns then render from the same source.

Appendix C

Environment hazards

Never run a production build while the dev server is up

This cost a full debugging session. The symptom is that a stylesheet edit is correct on disk and correct in the diff, but the browser shows the old value — and restarting the dev server, emptying the cache and hard reloading all change nothing, because none of them touch the cause. A concurrent build can leave the dev server pinned to bundler chunks it will not regenerate. That is a frozen module, not a stale browser.

Diagnose in this order. Confirm the source first, then fetch what the server actually serves rather than trusting the browser: request the page, extract the stylesheet chunk URL from the HTML, and fetch that chunk directly. If source and served disagree, touch the stylesheet, request the page again, and check whether the chunk's modification time moves. If it does not move, the watcher is dead and no amount of restarting will help.

Fix: kill every node process belonging to this project, delete the build output directory, restart. A restart alone is not enough — the cache is on disk and survives it. Identify the processes by command line so you do not kill processes belonging to the user's other projects; there are usually three.

Build environment variables

A production build may need environment variables that are not in the working tree, because page-data collection executes API route modules. Compilation and type checking pass without them; the build dies later. Work out the failure order once, write the incantation with throwaway values into your notes, and note that some clients validate the shape of a key at construction, so the dummy value must look plausible.

The dev server generally needs none of this for visual work.

Shell quoting

Where a tool wraps commands in a single-quoted shell invocation, an apostrophe inside a heredoc can terminate the quoting and fail with an unexpected end-of-file error. This is environment dependent rather than universal, so treat it as a hazard to recognise from the error message rather than a standing ban. For any file containing prose, prefer a dedicated write tool over a heredoc. Do not assume Python is on the path for text surgery.

Appendix E

The common layer

The canonical values for everything on the fixed list. Derived from the pattern guide once, during the first conversion, and signed off. Copy them verbatim.

Why this appendix exists

Every one of these values could be re-derived from the pattern guide. The reason not to is that two independent derivations will not agree — a clamp rounded differently, a shadow judged by eye, a tracking value estimated from a screenshot — and the disagreement will not be visible until two sibling sites are open side by side, long after both have shipped. This is the shared layer. It is group property.

Container

--container-wrap: 1160px;

.wrap { width: min(1160px, 100% - 40px); margin-inline: auto; }

1160px maximum, 20px gutters either side. Nothing on the site is wider.

The fluid type scale

Interpolated between the two viewport widths the guide is actually drawn at — 390px and 1440px. Both endpoints therefore land exactly on the guide's specification, which is what makes the browser walk at those two widths meaningful.

--fs-h1p:   clamp(1.9375rem, 1.45rem   + 2vw,      3.25rem);   /* 31 -> 52 */
--fs-h2:    clamp(1.75rem,   1.425rem  + 1.3333vw, 2.625rem);  /* 28 -> 42 */
--fs-h3:    clamp(1.375rem,  1.3054rem + 0.2857vw, 1.5625rem); /* 22 -> 25 */

--fs-h1 is the homepage hero heading; --fs-h1p is the interior-page hero variant, which typically drives every service, category and article route, so it has more call sites than anything else on the list. --sec-y is the vertical section rhythm and --header-h the sticky header height.

Body text is held flat at 16px deliberately

Below 16px, iOS zooms the viewport on input focus. Do not make body text fluid.

Geometry and shadows

--radius-btn:  4px;
--radius-tile: 4px;
--radius-card: 12px;

Cards are noticeably rounder than controls; that contrast is part of the look. Three shadows only, and they are used sparingly — the register is flat, so a shadow is an exception rather than a default. Hover states change border colour only: no lift, no shadow change, no scale.

Type roles

The faces are fixed; the weight is negotiable

A display-face swap was prototyped during the first conversion — Spectral and Source Serif 4, both rendered live against Newsreader on the comparison page — and rejected. The face does not move. Display weight did move, from 300 to 400, because the light cut read as too fragile at desktop sizes. That is a by-eye call, made with the user, and it is the only typographic dial you should expect to turn.

If you do change weight, change it everywhere at once. Leaving one display token behind is how an interior page ends up with a heading lighter than the subheadings beneath it.

Exactly one media query

@media (max-width: 767px) { /* ... */ }

Everything else interpolates. The query exists for the two things that cannot: display heading tracking and leading, which do not scale linearly with size, and the hero wash geometry. If your display face is a light cut, it also carries a weight bump here, because a light serif shreds below about 30px. Resist adding a second breakpoint.

Framework mechanics that will otherwise cost you an afternoon

The layer contract

The framework declares its cascade layers and leaves the components layer empty for you. Every hand-written class goes inside that layer, so utilities always out-rank it and class="card p-0" behaves as expected. An unlayered class beats every utility on the site, and the symptom is a utility that mysteriously does nothing on one component.

@layer theme, base, components, utilities;

@layer components {
  .card { /* ... */ }
}
Inline theme variables are not emitted to the root

Variables declared in an inline theme block are available to utility generation but are not written into :root. A component class referencing one gets nothing. Reference the variable name that is actually emitted, and declare colour tokens in a static theme block precisely because that forces them into :root even when no utility references them.

Preflight fights the guide

The reset zeroes heading size and weight, strips list markers, and makes links inherit colour. The guide assumes none of that, so every heading and list class must restate what it wants.

Do not copy the guide's global coloured link rule. It will turn the navigation, the breadcrumbs and the footer brand-coloured. Inline links opt in through a .link class; article bodies get it automatically through the prose class.

What the guide does not define, and the group has settled

The guide is a static mockup: it contains one hover rule and no focus, transition, disabled or keyframe styling at all. These were designed once and belong to the group, not to any one site.

  • A global :focus-visible ring, which recolours over dark contexts — the dark panel and the footer — so it stays visible on every ground.
  • An explicit disabled fill on the primary button. Reduced opacity alone is near-invisible on a light button.
  • html { scroll-padding-top: calc(var(--header-h) + 16px) }, because smooth scrolling plus a sticky header otherwise lands every anchor underneath the header.
  • Hover is border colour only. Stated again because it is the rule most often broken by reflex.

Icons

A thin-stroke set traced from the guide: arrows, check, chevrons, plus, minus, close, menu, a quote glyph and a star. All currentColor, all aria-hidden, sized 11–20px at stroke weight 1.5–1.8.

Where a third-party icon library is also in use for section or category glyphs, pin the stroke weight to 1.6 at a 16 or 20px box on every single use. The library defaults are far heavier and will read as a different design system sitting inside yours.

Icons take the brand's dark reading tone, never the bright signal tone — at these stroke weights the signal tone reads washed out even where the contrast ratio technically passes.
